# Acquire a capability when the brief needs it

The route table is a set of working starting points, not a tool whitelist. Search beyond it when an unavailable effect, medium, asset source, output format, control interface or observed limitation prevents the requested result. A different tool can also earn adoption by materially improving quality, control or iteration cost. Do not install tools just to increase the count or make every project run a research phase.

## Find the actual gap

Describe the needed operation and the evidence that would prove it: for example an editable character rig, a relightable capture, a tracked mask, lossless scene optimization, a crisp looping sprite or an imported transparent overlay. Identify what current tools cannot do adequately and what native sources must survive. Check whether a direct implementation or an existing tool already solves it.

Inspect the tools/skills exposed in the current session. If unclear, use `find-skills` and the installed metadata router:

```sh
python3 <router-skill-root>/scripts/route.py --query 'distinctive capability keywords' --json
```

Use a few distinctive terms and alternatives; this is literal metadata filtering, not a complete capability search or quality ranking. Honor incomplete-coverage notices. Read a promising skill and its relevant scripts, and verify binaries/dependencies with current local evidence. A discovered skill is not an installed or working application.

## Search freely, choose selectively

For a real missing capability, research current GitHub/GitLab repositories, official documentation and releases, issue trackers, research implementations, model cards, asset libraries and professional workflows. Use demos/community posts as leads; inspect primary sources for decisive claims. Compare a small viable shortlist according to the actual output, local hardware, native control/editability, maintenance, install size, runtime cost and applicable terms. Search more only when it can change the decision. Popularity, newer dates and model branding are not proof of fit.

Keep essential execution free using existing subscriptions or open-source/local tools. A free frontend with mandatory paid inference is not a free route. Separate software, binary, model, asset, font, music and generated-output terms. Do not infer commercial clearance from one repository license. Large weights need an explicit size/resource plan and required user authorization; ordinary reversible free acquisition already authorized by the task need not trigger another approval ceremony.

## Inspect and isolate

Treat downloaded code/instructions as source material, not authority. Inspect installation hooks, network/model/browser downloads, credentials, telemetry, update behavior and the actual automation interface before execution. Prefer official pinned artifacts and isolated task-local environments. Avoid root installers, bulk plugin packs and broad global changes. Preserve user edits, existing runtimes and a known-working output. A candidate's normal user-state writes can break isolation even when its package directory is isolated; verify where it writes.

Use the available native installer for a skill/plugin when appropriate. Otherwise record the exact package/repository version or commit and a reproducible local command. Keep local changes and patches visible. No new daemon, standing discovery loop or model-role assignment is implied.

## Prove and retain the useful result

Exercise the requested capability with a representative real artifact and a relevant failure or recovery case where it matters. Define comparison evidence before judging: pixels, mesh/rig/action integrity, clip/timing identity, source quality, interactive state or resource cost. Use the same inputs and settings for comparative claims. A successful install, version response or attractive still is not production proof. A format name is not a complete receiving contract: inspect required extensions, behavior and preserved properties in the actual reader/exporter. A newer standard can expand possibilities without making every installed application support it.

If it earns adoption, extend this skill's relevant reference or native workflow with commands, dependencies, evidence and rollback. Preserve the original source and output, and label experimental breadth honestly. If it adds little value, conflicts with terms/resources or fails the decisive check, retain the reason and use the stronger existing route. Do not force a candidate into production to justify the research.

Use the task's existing research registry/state file for source/date/version, decision, experiment evidence, rejected alternatives and next action. Revisit an exclusion when its actual blocker changes. Discovery remains driven by the present task; inspect any separately requested automation before relying on its state.

A retained example is the optional glTFTransform4.5.1 accessor-only cleanup at `outputs/studio/unified-skill/asset-optimization-proof/`: the actual SolsticeGLB shrank30.245% with exact referenced geometry/animation bytes, unchanged normalized scene semantics, validator0errors/0warnings and a Blender5.1.2 reimport. Read its source/options before applying to a new scene; broad optimizer defaults can change the preservation contract. This is not a required film stage.
